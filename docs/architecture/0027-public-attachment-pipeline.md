# ADR 0027: Secure public attachment pipeline

## Status

Accepted for PR 25.

## Context

The document subsystem already supports immutable versions, SHA-256 integrity
metadata, quarantine state, malware-scan state, submission links, case links,
and trusted-download checks. Public intake forms also have a generic `file`
field type, but the browser control was intentionally disabled because there
was no safe transport policy connecting an untrusted public upload to those
document primitives.

A reusable public-intake application needs to accept supporting files without:

- trusting a browser-supplied document category;
- placing binary data in ordinary submission JSON;
- making unscanned content visible as evidence;
- allowing MIME or size policy to drift away from the configured document type;
- losing provenance between intake, scanning, and later case use.

## Decision

A file field may opt into public upload only with explicit manifest policy:

```json
{
  "id": "supporting_files",
  "type": "file",
  "acceptedMimeTypes": ["application/pdf"],
  "maxFiles": 3,
  "publicUpload": {
    "documentTypeKey": "supporting_material",
    "visibility": "internal"
  }
}
```

The application manifest must declare the referenced document type. If the
file field declares MIME types, they must be a subset of the document type's
MIME policy.

Browser `File` objects are not persisted in the submission answer map.
Instead the public upload path:

1. resolves the immutable published form definition;
2. applies visibility and field policy;
3. enforces file-count, per-file deployment size, aggregate submission size, document-type size, and MIME limits;
4. reads the bytes and computes SHA-256;
5. writes an opaque object through the configured storage adapter;
6. persists an immutable document/version linked to the submission;
7. stores only document-version IDs as the file-field answer references;
8. records custody, access, and immutable audit metadata.

## Quarantine boundary

Every public upload begins with:

```text
content_status = quarantined
malware_scan_status = pending
```

Acceptance by the web server is not a clean scan.

The engine still requires a real malware scanner or an authorized external
scan result. It never ships an implicit scanner that marks content clean by
assumption.

A clean result changes the version to `available / clean`. An infected result
changes it to `blocked / infected`. Failed or pending scans remain
quarantined.

## Evidence promotion

Submission attachments do not satisfy case evidence requirements while they
are quarantined.

When a case is created from a submission, only already-clean submission
versions are linked into the case evidence set.

If a scan becomes clean after case creation, the scan transaction promotes
that version into the source case. Conflict-safe insertion prevents duplicate
case links.

Therefore both event orders are supported:

```text
upload -> clean scan -> case creation
upload -> case creation -> clean scan
```

In both orders, only clean content reaches the trusted evidence surface.

## Integrity and failure handling

The storage key is generated by the engine and contains no user-supplied path
components. Filenames are sanitized for metadata display only.

The web transport is capped at 64 MB for server-action multipart bodies. Within
that transport boundary, `PUBLIC_UPLOAD_TOTAL_MAX_BYTES` defaults to 50 MB and
limits the combined accepted attachment bytes for one submission. Individual
files remain subject to `DOCUMENT_MAX_BYTES` and document-type limits.

If validation fails after one or more objects have been staged, those staged
objects are removed. If the submission database transaction fails, staged
objects are also removed by the request path.

Downloads retain the existing trusted-document contract: content must be
available and clean, and SHA-256 is recomputed from stored bytes before the
download is returned.

## MIME limitation

Browser-reported MIME type is a policy gate, not a content-authenticity
guarantee. Production malware/content inspection remains responsible for
examining the actual file content. This PR does not claim that a
`Content-Type` value proves file format.

## Security boundary

This capability handles ordinary untrusted public files. It does not:

- create a classified-information channel;
- encrypt file content into protected form compartments;
- make participant-message attachments available;
- provide a malware-scanner product by itself;
- replace deployment-specific object-store, sandbox, DLP, or accreditation
  controls.

Downstream applications must continue to state their own information-handling
boundary accurately.
