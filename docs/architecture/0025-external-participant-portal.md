# ADR 0025: Protected external-participant portal

## Status

Accepted for PR 23.

## Context

Some intake applications must let a person who is not an authenticated staff user securely check status and exchange messages after a public submission.

A confirmation/receipt code is intentionally non-secret and therefore cannot serve as an authentication credential.

Creating application-specific public lookup endpoints would also risk exposing internal case fields, duplicating messaging logic, and encouraging downstream forks of security-sensitive behavior.

## Decision

Forms may opt into a generic participant portal through versioned form policy:

```json
{
  "participantPortal": {
    "enabled": true,
    "allowMessaging": true
  }
}
```

Final submission issues two values:

1. the existing confirmation/tracking code, which remains non-secret;
2. an independent 256-bit random access secret.

Only the SHA-256 hash of the access secret is persisted.

The raw secret is returned only in the successful form-action result. It is never placed in a URL or persisted for later recovery.

## Authentication and sessions

Portal authentication requires tracking code + access secret.

Login is rate-limited through a dedicated participant bucket using the existing durable throttle mechanism.

A successful login creates a separate opaque participant session token. Only its hash is persisted.

Participant session cookies are:

- HttpOnly;
- SameSite=Strict;
- Secure in production;
- scoped to `/participant`;
- time limited.

Participant sessions do not create a `users` row or organization membership and never enter the staff RBAC model.

## Exposure boundary

The participant context is derived server-side from:

```text
session
 -> credential
 -> source submission
 -> optional case
```

The public participant model contains only:

- tracking code;
- submission timestamp;
- case number, if one exists;
- current workflow-state label;
- case updated timestamp;
- portal correspondence with participant/public visibility.

It intentionally omits all ordinary submission answers, protected values, title, summary, priority, assignment, queue, deadlines, reviews, notes, audit records, and non-portal correspondence.

## Messaging

The portal reuses the existing case communication tables.

Staff create normal outbound correspondence with:

```text
channel = portal
visibility = participant | public
```

Publishing such a message transitions it directly to `sent` with provider `participant-portal`. No external transport or delivery job is created.

Participant replies are normal inbound correspondence with:

```text
channel = portal
visibility = participant
provider = participant-portal
```

The audit actor is anonymous/external rather than a staff user.

A participant may reply only to a thread that already contains participant-visible portal correspondence for their own case.

Portal attachments are rejected until a dedicated participant-safe document-delivery contract exists.

## Caching and indexing

All participant routes are private/no-store and carry noindex metadata.

Secrets are not placed in query strings, fragments generated by the server, or confirmation URLs.

## Scope

This capability is a protected per-submission participant channel.

It is not:

- a general external user-account system;
- identity proofing;
- credential recovery;
- classified-system accreditation;
- public attachment intake;
- participant document download.

Those require separate reusable contracts.
