# ADR 0034: Immutable release-request dispatch

## Status

Accepted for PR 34.

## Context

PR 33 made the validated container release workflow manually dispatchable from
GitHub Actions.

The connected repository automation can create branches, commits and pull
requests, but it cannot directly invoke `workflow_dispatch`.

Future releases should still be triggerable through the normal reviewed Git
change path without falling back to local tag creation or a personal access
token.

GitHub permits a workflow using `GITHUB_TOKEN` to create a
`workflow_dispatch` event. This is one of the explicit exceptions to the
general workflow-recursion suppression applied to events generated by
`GITHUB_TOKEN`.

## Decision

The repository supports a root-level:

`release-request.json`

A change to that file on `main` triggers:

`.github/workflows/release-request.yml`

The request schema is:

```json
{
  "schemaVersion": 1,
  "version": "1.0.0-rc.9",
  "sourceRef": "<40-character immutable Git SHA>"
}
```

The request validator requires:

- schema version 1;
- a valid release version;
- version exactly equal to `package.json`;
- `sourceRef` to be a full immutable 40-character Git SHA.

Moving refs such as `main` are rejected.

After validation, the request workflow dispatches `release.yml` with:

- the requested version;
- the immutable source SHA.

The validated release workflow remains responsible for:

- verifying the package version at the requested source;
- checking release-tag state;
- the complete release test/build gates;
- safe tag creation;
- GHCR publication;
- provenance/SBOM;
- Actions and GitHub Release evidence assets.

## Why the request does not create the tag itself

Release-request automation is deliberately a thin dispatcher.

Tag state and container publication stay centralized in the validated release
workflow so there is one release authority and one retry policy.

## Security

The dispatcher has only:

- `actions: write`;
- `contents: read`.

It does not receive package-write or contents-write permission.

The downstream release workflow separately receives the permissions it needs
for tag and package publication.

A release request therefore cannot bypass the release workflow's version,
source, tests, tag-state or evidence checks.

## Operational use

A release can be requested through a normal reviewed PR that changes only
`release-request.json`.

After that PR is merged to `main`:

1. the request workflow validates the immutable source SHA;
2. it dispatches the release workflow;
3. the release workflow performs the full release;
4. downstream applications consume the resulting public
   `release-evidence.json`.

## Retry behavior

Updating or re-merging a request for the same version/source is safe because the
release workflow permits an existing tag only when it resolves to the exact
same source commit.

## Scope

This mechanism requests a release. It does not:

- deploy downstream applications;
- change a release tag;
- bypass release validation;
- store production secrets.
